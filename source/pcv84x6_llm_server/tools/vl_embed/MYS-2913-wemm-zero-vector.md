# WeMM 重复推理零向量：10151 板端隔离复现与根因分析（MYS-2913）

日期：2026-11-16　设备：172.26.166.96:10151（sophon，linaro）
服务：cv84x6-llm 0.6.37　模型：wemm-embedding-2b（W8BF16, seq2048, buckets, gdnmixed）

## 结论

**根因是宿主侧（host）异步设备操作的完成顺序没有被保证，不是模型、不是 bmodel、不是驱动、也不是 NPU 显存不足。**

`native/src/vl_embed_engine.cpp` 用 `bm_memcpy_d2d_byte`（`copy()`，:92-98）把上一步的输出搬进下一张图的输入缓冲，然后立刻 `bmrt_launch_tensor_ex` 启动下一张图（`launch()`，:99-120）。这两个 API 都不保证"搬运已落地"。当 TPU 在搬运完成前就开始读那块缓冲时，它读到的是上一次留下的内容或未初始化内容；严重时整个输出向量为 0，被 :384 的全零检测拦下并置 fault（后续必须 reload）。

同一缺陷还有一个**更容易被忽略的后果**：即使没有触发零向量，同一条输入每次返回的向量也不同。这不是精度抖动，是不同输入互相污染。

实测（同一进程、同一 handle、同一输入连续 6 次）：

| 路径 | 故障数 | 不同向量数 | 最差余弦 |
|---|---|---|---|
| 出厂库，长文本（bucket 512） | 4–6 / 6 | 0–5 | 0.26–0.50 |
| 出厂库，短文本（bucket 128，"正常"路径） | 0 / 6 | **6 / 6** | **0.61** |
| 出厂库，图片 384×512（bucket 512） | 0–4 / 4 | 3 / 4 | **−0.0198** |

图片路径最严重：同一张图两次返回的向量余弦可以是 **−0.02**，即两个基本无关的向量。服务此前把这条路径当作"成功"返回给用户，索引里存的就是这种向量。

## 已证实的事实

1. **现场版本与输入完整核对一致。** 服务 0.6.37；`libcv84x6_llm.so` SHA256 `b2363e3e…f61b32`；bmodel SHA256 `480a6742…9713bd`（3121778688 bytes），与发布输入逐位一致。主机身份按确认的指纹 `SHA256:iYClJgKTiA9TOMyvJL8QeBndKqY9wbhKsTbyNH9vHo0` 严格校验后连接。

2. **现场故障序列（只读，来自 `state/inference_records.sqlite3`）。** 18:07:23 图片 204 tokens 成功 → 18:07:39 同模型 zero vector → 之后 fault；重载后 18:10:47/49/51 纯文本 62 tokens 连续成功 → 18:11:18 图片 177 tokens 成功 → 18:11:22 zero vector。两次失败都紧跟一次图片请求。

3. **不需要图片也能复现。** 纯文本（205 tokens，选中 bucket 512）连续 6 次：4–6 次报 `encoder returned a zero vector`。所以"图片触发"是表象；真正相关的是**选中哪一档静态图**和**时序**，图片只是让单次调用变长、更容易撞上窗口。

4. **不需要触发零向量就已经错了。** 短文本 bucket 128 从不报错，但同一输入 6 次返回 6 个不同向量（最差余弦 0.61）。这条路径现场一直"成功"，用户拿到的向量本身不可复现。

5. **逐层数值摘要：各层都正常。** 在诊断副本里加了逐层回读（token embedding、ViT 输出、24 个 block 的输入/输出行），所有阶段 norm 均非零（embed 0.481、ViT 6.167、各 block 正常）。零值不在某一层"算错"，而是**读到了不该读到的缓冲内容**——回读这个动作本身会强制同步，加上回读后故障消失（见第 7 条）。这与"共享内存/编译图/量化"假设都不符。

6. **缓冲地址无重叠。** 导出所有图 stage-0 缓冲与引擎自有 `hidden` 的地址区间，互不重叠；`block_s512[*]` 复用固定两块输入/输出，`hidden` 独占 `0x12f3e8d000..0x12f468d000`。所以不是简单的地址别名。

7. **决定性对照（每次只改一个因素，同一输入）：**

| 实验 | 故障 | 不同向量 | 最差余弦 |
|---|---|---|---|
| 出厂行为（无任何等待） | 13/18 | 5 | — |
| 每个 d2d 拷贝后 `bm_thread_sync` | **0/18** | 1 | **1.0** |
| 每个 d2d 拷贝后**纯 CPU 延时 2ms**（完全不碰设备） | **0/18** | 1 | **1.0** |
| 每个 d2d 拷贝后纯 CPU 延时 **50µs** | **0/18** | 1 | 1.0 |
| 只在 launch 前 `bm_thread_sync` | 24/24 | 0 | — |
| 只同步 `embed` 拷贝点 | 17/18 | 1 | — |
| 只同步 `block` 拷贝点 | 12/18 | 6 | 0.08 |
| 只同步 `vit` 拷贝点 | 15/18 | 3 | 0.92 |
| 只同步 `wemm` 拷贝点 | 5/18 | 7 | 0.45 |

   两条关键推论：
   - **纯 CPU 延时（不产生任何设备同步）也能 100% 消除故障**，说明这是**时序竞态**，不是"少了一次同步调用"这么简单；任何让宿主慢下来的因素都会掩盖它。这也解释了为什么之前的 216 条验证和 98 项目录验收全部通过——那些跑法每次请求之间的额外工作把窗口躲开了。
   - **只在 launch 前同步无效**（24/24 全故障），说明问题不在"launch 之前有没有排空"，而在拷贝提交与图执行之间的**具体交错**；只在某一个拷贝点同步也只减轻不消除，说明多个拷贝点都在竞争。

8. **驱动无异常。** 全程 dmesg 无 NPU 超时、无 OOM、无新增驱动错误；故障纯属宿主侧顺序问题，与 MYS-2703 那类 TPU 卡死不是一回事。

## 假设与未解决问题

- **假设（未直接证实）：** `bm_memcpy_d2d_byte` 在本板 libsophon 0.4.15 上是异步提交（CDMA 队列），`bmrt_launch_tensor_ex` 与它不共享完成序；`bm_memset_device_ext` 同理。手册没有给这两个 API 任何完成保证，实测行为与"异步"一致。要坐实需要 libsophon 源码或厂商确认——当前板端只有头文件与二进制。
- **未解释：** 为什么"launch 前同步"反而 100% 失败。可能是该同步把拷贝与 launch 压进了同一条更窄的交错窗口，也可能触及了 bmrt 内部队列的另一条路径。这一点没有定论，不臆测。
- **未验证：** 修复后长时间稳定性、与其他模型（reranker/OCR）并发时的表现、以及 4 核满载下的行为。

## 最小修复方向（本任务不部署）

优先顺序：

1. **拷贝后建立完成序**（实测 0/18 故障，最稳）：在 `copy()` 与 `zero()` 之后按需 `bm_thread_sync`。代价是每层多一次同步；只对"喂给下一张图的拷贝"同步即可，不必对所有拷贝同步。**不要**用纯延时——那只是把窗口挪走，换个负载就会复发。
2. 若性能不可接受，改用**双缓冲 + 每层一次同步**：整层所有拷贝提交完，同步一次再 launch，把同步次数从每层 3 次降到 1 次。
3. 修复后必须新增**回归门槛**：同一输入连续 N 次，要求向量**逐位一致**（不是"余弦 > 0.99"）。当前测试集全是单次调用或跨输入比较，天生看不见这个缺陷——这是 216 条验证漏检的真正原因。

同时应修（与本缺陷独立，但同一条链路上会误导排查）：
- `app/api/tool_calls.py:85` 用"文本非空"判断支持，纯图输入的 `text=""` 被拒；
- `app/api/openai_api.py:803` 给纯图记录拼接空 text；
- `app/core/inference_log.py:1079` 捕获后继续推理。
这三处只影响请求记录，**不是**零向量的原因，修了也不会让零向量消失。

```bash

  --library /opt/sophgo/cv84x6_llm_server/lib/libcv84x6_llm.so \

  --library ... --model ... --config ... --output /tmp/repeat-probe.json

# 3) 走真实 HTTP + worker 栈（最接近现场）
PYTHONPATH=/opt/sophgo/cv84x6_llm_server/vendor:/opt/sophgo/cv84x6_llm_server \

```

图片全部由固定种子合成 PNG，不需要客户原图；每个 group 用独立进程/独立 handle；不碰 8000 端口、不改线上模型目录、不重启线上服务。
