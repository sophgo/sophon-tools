# 按模型配置：空闲卸载、按需加载、设备内存上限（MYS-2675）

三件事，每个模型单独配置，互不影响：

| 字段 | 类型 | `null` 的含义 |
|---|---|---|
| `idle_unload_min` | 整数 0–1440 / null | 跟随**全局**设置（`aux_idle_unload_min`） |
| `auto_load` | bool / null | 跟随**全局**设置（`aux_auto_load`） |
| `mem_limit_mb` | 整数 64–1048576 / null | 跟随**本模型推算出来的**默认上限 |

设置持久化在 `state.json` 的 `model_settings[<模型 id>]`，删除模型时一并删除。
`null` 不是 0、也不是空串：它是「没配过，用默认值」的显式写法，`PUT` 里传
`null` 就是「把这个字段恢复默认」。

## 一、全局设置的含义变了（但行为没变）

`aux_idle_unload_min` / `aux_auto_load` 仍然存在，含义改为「**没有单独配置的模型
用的默认值**」。关键一点：**这份全局默认仍然只作用于 `AUX_KINDS`**
（`embedding` / `rerank` / `asr` / `ocr`）。

于是：

- 已有安装升级后行为**完全不变**——v0.6.27 打开全局开关的操作员，得到的还是那四类
  辅助模型被管、35B 不被管；
- `chat` 与 `ocr_vl` 只有**点名单独打开**才进空闲机制。这是刻意的：35B 装载要几十秒，
  agent 依赖它常驻；OCR-VL 2.27 GB、装载约 8 秒，一页识别是一串请求，卸载的收益会在
  下一次装载上赔回去；
- 反过来，任何模型都可以单独**关掉**：给它设 `idle_unload_min = 0`（0 是一个值，
  不是「未设置」），它就再也不自动卸载，即便全局默认是开着的。

生效值的算法就三步（`ModelManager.effective_idle_minutes` / `effective_auto_load`）：

```
模型有该字段的单独值？  -> 用它（任何 kind 都算数）
否则 kind 在 AUX_KINDS？ -> 用全局值
否则                    -> 0 / false
```

接口同时给出原始值和生效值：`settings` 是操作员存下的（含 `null`），`effective`
是此刻真正在用的。界面应当据此区分「这个数是操作员选的」和「这个数是默认值」。

## 二、设备内存上限

### 三个数

| 字段 | 含义 | 来源 |
|---|---|---|
| `mem_static_bytes` | **静态占用**：权重 + neuron + 指令，加载完即为常驻 | 加载时实测的设备堆差值；从未加载过则用 `bmrt_get_bmodel_info` 估算 |
| `mem_used_bytes` | **占用估计** = 静态 + 按 token 长度估算的会话 KV + 前缀缓存；不含 park 取整及扩容峰值 | 静态值 + worker `stats` 里的 `kv_used_bytes` |
| `mem_limit_default_bytes` | 推算出来的默认上限 | 静态 + 运行期额度，按 64 MiB 向上取整 |
| `effective.mem_limit_bytes` | 生效的上限 | 单独配了就用它，否则等于上面那个默认值 |

### 加载时：静态超限就拒绝

`_check_mem_limit` 在 spawn 之前跑。静态占用 > 上限 → 409，提示里同时给出两个数：

```
模型 X 的静态占用 22752 MiB 超过本模型内存上限 8192 MiB，无法加载；
请调大该模型的内存上限（默认 23040 MiB）
```

在这一步拒绝而不是让 worker 去撞 `bm_alloc_gmem failed`，是因为上限小于权重时这个
模型**无论如何都服务不了任何请求**，而 worker 的报错既慢又不说明原因。

### 加载完：用实测静态值重新配置 worker（v0.6.34 起，MYS-2805）

上面的检查和 spawn 都用的是**加载前**的估算静态值（`bmrt_get_bmodel_info`），因为这一刻
还没有更好的数。动态 Build 的估算可能远低于真正映射的量（35B：声明 20122 MiB，实测
22752 MiB），于是 `上限 − 估算` 会给调度器多发一块它并不拥有的内存。实测复现（`.157`，
全新管理进程、9B）：上限 14355 MiB、实测静态 13978738688 字节，worker 运行期预算
5482284672 字节，正确值 1073569792 字节，多发 4408714880 字节。

所以加载的最后一步（`_spawn_and_await`）在发布 `loaded` **之前**做三件事，顺序固定：

1. 记录实测静态值（`_record_static_measurement`）；
2. `_check_final_mem_limit`：若实测静态 > 显式上限 → 拒绝加载并结束 worker
   （409 `model_mem_limit_exceeded`，提示里给出两个字节数）。不会「加载成功但预算为 0」；
3. `_sync_worker_budget`：用最终的静态字节和生效上限 `configure` 一次，并要求 worker
   回报的运行期预算**等于** `上限 − 实测静态`，然后再执行 `_commit_load_budget` 用实测
   占用重算设备准入。

配套要求（少了任何一条都会留下「已加载但预算无人确认」的状态）：

- 同步被拒绝、答复丢失、超时或取消 → **不发布 `loaded`**，走既有失败路径结束 worker。
  答复丢失（`WorkerTransportError`）不算拒绝：worker 可能已经应用，于是用一次有界的
  `stats` 读来判定，读不回来才算失败。
- 设备 free 已包含刚加载的静态占用，所以重算时**只**把运行期预算当作待承诺量，静态不重复扣；
  其他已加载模型的运行期预算与尚未完成的承诺照常计入，加载的原子临界区仍然只持有
  设备预算锁到「读—算—登记」为止。
- 未确认存活 worker 的预留在进程确认退出前不归还；退出被确认时随 `_forget` 一起清掉。

因此**冷启动后的预算与保存的额度一致，不需要再保存一次设置**。默认上限同样按实测值重算，
所以默认路径也不会因为估算偏低而多发。

### 加载时：NPU 至少留 1 GiB（防 TPU 卡死，D7）

`_check_npu_reserve` 在上面两条检查之后执行。它不问「这个模型放不放得下」，问的是「放下之后
NPU 堆还剩多少」：

```
NPU 当前空闲 − 本模型的占用 − 已加载的大模型的运行期预算 − 尚未完成的承诺 < 下限  →  409
```

- **下限默认 1024 MiB**，在 `server.env` 里设 `CV84X6_NPU_RESERVE_MB` 可调整，`0` 表示关闭。
  依据是 10155 上的实测：负载不变、只改剩余量时，剩 280 / 512 MiB 约 2 分钟必定卡死，
  剩 640 / 1024 MiB 跑 12 分钟正常；开启后用 4 模型 + chat×2 跑 60 分钟、2027 次请求，无卡死。
  见 `docs/research/d7-tpu-hang.md`「修复实验」一节。
- **本模型的占用**：大语言模型和 PaddleOCR-VL 按上限（静态 + 运行期预算）计算；Embedding、
  Reranker、ASR、OCR 按静态 + 256 MiB 加载余量计算。原生辅助引擎在加载时就分配完全部内存，之后不再增长，
  它们的「运行期预算」只是配置值，不计入「已占用」。
- **已加载的大模型按整份运行期预算计入**（不是「尚未用掉的部分」）：那是一个按 token 估算的
  数，不是已落地的分配，抵回来就会拿没被证明存在的内存做承诺。见下面「运行时增额」一节的说明。
- **大模型按上限而不是静态计算**：35B 加载后，会话和前缀缓存还会再长出它的运行期预算
  （默认约 462 MiB）。只按静态计算，加载时刚好剩 1 GiB 的板子运行一段时间后会跌到约
  560 MiB，正落在实测会卡死的区间（512 卡死、640 正常）。
- **只看 NPU 堆**：所有卡死现场里，VPP 都停在启动时保留的 256 MiB。
- **实际影响**：32 GB 的板子默认不能同时装下全部 6 个模型（35B + Embedding + Reranker
  + ASR + OCR + VL），最后一个会被拒绝，提示里写明还剩多少、当前加载了哪些。
  确实需要 6 个模型共存时，可以调低下限，但那样就回到了已知会卡死的区间。

### 运行时：会话与前缀缓存的预算 = 上限 − 静态

`chat` 与 `ocr_vl` 的调度器把 `kv_budget_bytes` 收到 `min(上限 − 静态, 设备还能给的)`：

- `Scheduler._fits` 用这个预算判断新请求能不能加入已运行的会话；
- 放不下就**排队**（FIFO，不跳过），不是失败；
- 队列满了才 429，提示里写明是本模型内存上限；
- **前缀缓存的字节上限就是这个预算本身**（见下一节），缓存给会话让路。

改上限**不需要重新加载**：`PUT` 之后管理面通过 `configure` 把新的
`--mem-limit-mb` 推给运行中的 worker，调度器在每次准入时重读
`kv_budget_bytes`，缓存上限同时跟着改。调大无需等待；调小必须等运行中的请求结束，否则 worker 拒绝、API 返回 409，原设置不变。空闲时调小立即裁剪缓存。恢复默认也遵循同一规则。
这一条能成立是因为 `apply_mem_limit` 每次都从**加载时保存的设备预算**重算
`min(上限 − 静态, 设备余量)`，而不是在旧值上再做一次 `min`——后者只会单向变小。
（**这个设备预算是加载时的读数，只回答「worker 自己还能给多少」，不代表板子现在还能
承诺多少**；增额能不能许出去由管理面在 PUT 里另外判定，见下一小节。）

其他 kind（embedding / rerank / asr / ocr）的引擎没有跨请求 KV，一次调用就是一次
前向，缓冲是固定的，所以它们的上限**只在加载时检查**，运行期不再收。

### 运行时增额也要过设备准入（v0.6.34 起，MYS-2795）

上面那段「改上限不需要重新加载」只说了怎么把新数字送进 worker，没说这个新数字**能不能**
给。v0.6.34 之前的答案是「能」：`PUT` 直接把 `mem_limit_mb` 推给 worker，worker 用
**加载时**存下的 `device_budget_bytes` 重算 `min(上限 − 静态, 设备余量)`。那次读数一旦
过时——别的模型加载了、释放了——它就不再代表板子现在还能承诺多少，而加载路径上的
`_check_npu_reserve` 根本不在 PUT 的处理链上。

复现（负责人 `reproduce_live_raise.py`）：模型已加载、运行期预算 400 MiB，管理面读到
NPU 空闲 1024 MiB、下限 1024 MiB，把额度调到 1000 MiB —— **返回 200，设备余量检查调用
次数为 0**，worker 拿到 1000 MiB。

现在加载与增额共用**同一套算术、同一个短临界区、同一份承诺账本**：

```
NPU 当前空闲 − 本次新增的承诺 − 已加载(chat/ocr_vl)的运行期预算（含目标自己） − 尚未完成的承诺
                                                          ≥ 下限(默认 1024 MiB)
```

- **本次新增的承诺**：加载是模型占用，增额是**新旧运行期预算之差**（不是整份新预算——那会把
  目标原来的预算算两遍）。
- **已加载大模型的运行期预算：整份扣，包含发起增额的那个模型自己**。这一条是首轮验收
  的第一处发现，也是本卡最容易写错的地方：

  `free` 是 bmrt **此刻**报的余量；模型的运行期预算是一份它**可能**还会用掉的承诺，不是已经
  落地的分配。所以既不能把「已用部分」抵回来，也不能因为「它就是发起方」而把自己那份排除掉
  ——那等于把同一批字节花两次。判据是

  ```
  free − 所有已加载 growing 预算 − 本次增额 − pending ≥ 下限
  ```

  举例：原预算 400、调到 1000、下限 1024，则 `free` 至少要 **2024 MiB**（400 + 600 + 1024），
  不是 1624。1624 只剩 624 MiB，正落在实测会卡死的区间。

- **不按「已用」抵扣。** `runtime_bytes` 是按 token 长度估算的，不含 park 按 4096 槽取整、
  也不含扩容时旧缓冲与新缓冲同时在世的峰值，因此它**不是**可精确抵扣的物理分配量。用估算值
  抵扣去换放行，就是拿没被证明存在的内存做承诺。代价是**缓存/会话很多时可能拒掉物理上放得下
  的增额**——这一句就是那个代价的说明：**需要更大额度时先卸载其他模型再调**。这一轮不做不可靠
  的抵扣。
- **尚未完成的承诺**：准入通过就登记，加载/增额真正完成前一直占着。加载要几十秒，这几十秒
  里它占的内存不能被第二个准入当成空闲。登记在检查**通过的那一刻**、在同一个临界区里完成，
  所以不存在「放行了但还没记账」的空窗。
- **所有有 NPU 占用的模型都要登记，包括辅助模型**（首轮验收的第二处发现）。「辅助引擎加载后
  不再增长」是真的，但不相关：它在**加载过程中**就要占满自己的 footprint，两个 embedding 同时
  加载若都按同一份空闲额放行，就会超卖一个。登记额度按 kind 与检查同源：
  `chat`/`ocr_vl` 用「静态 + 运行期预算」，其余用「静态 + `AUX_DEVICE_HEADROOM`」。
  辅助模型加载完成后**不保留**运行期承诺（它会由 `loaded` 与检查里的静态+余量规则描述），
  所以不会永久多算一份。
- **下限为 0 时关闭**：`CV84X6_NPU_RESERVE_MB=0` 的语义不变，增额照旧放行。
- **设备读不到余量时**：`native` 后端返回 **503**（不是按「空间充足」放行）——增额是把内存
  提前许出去，看不见堆就没有依据许。`mock` 后端（开发机、测试）保持可测，无读数照常放行。
- **拒绝的表现**：HTTP **409**，`code` 为 `device_memory_insufficient`，原设置与 worker
  额度都不变（检查在 `configure` 之前，所以 worker 根本没被碰过）。

#### 事务收尾：确认真的不再生效，才释放承诺

首轮验收的第三处发现。原来 `PUT` 用一个 `finally` 无条件释放承诺，于是

* `configure` 超时 / 连接断开 / 请求被取消 —— 这三种情况下「worker 拒绝了」和「worker 已经
  应用了，只是答复丢了」**看起来一样**。当成拒绝处理，就会报「409，什么都没变」，而 worker
  实际已经跑在新额度上，同时账本清零、那部分内存对后续准入完全免费。

第二轮验收（MYS-2801）又发现这条链上有三处没闭合，各自的原因不同：

* **传输失败被当成拒绝**。`WorkerClient` 在本地连接失败、写失败、或读到 EOF 时也抛
  `WorkerError`，和 worker 答复的 `{"error": ...}` 是同一个类，于是 `admin_api` 一律当拒绝。
  现在两者分开了：worker 真的答复才算拒绝，本地链路问题抛 `WorkerTransportError`
  （`WorkerError` 的子类，`transport = True`，`stage` 为 `connect`/`write`/`read`），
  既有调用方照旧捕获 `WorkerError` 不受影响。
* **未确认状态出不去**。`raise_if_budget_unresolved` 对每一次新保存都返回 409，
  连它自己提示的「重试同一次保存」也拒绝，卸载同样拒绝，于是承诺只能靠重启进程清掉。
  现在重试**先核对**：同一个额度会先读 worker 实际状态再收敛，只有**不同的**变更才 409。
* **持久化半写**。`StateStore.set_model_settings` 先改内存字典再 `save`，`save` 抛错时
  内存里留着新值、磁盘还是旧值，而 worker 已经回滚——三方读数互相矛盾。现在改字典、保存、
  失败则把原 entry 放回（包括「原本没有 entry」和「`null` 恢复默认」），且不触碰其他模型。

所以释放与否由**已知事实**决定，而不是由有没有抛异常决定：

| `configure` 的结果 | 事实 | 收尾 |
|---|---|---|
| worker 答复并拒绝（`{"error": ...}`） | 没有应用 | 立即释放承诺，409 |
| worker 答复并应用 | 已应用 | 先保存设置，再释放（设置从此承载这份承诺，无空窗） |
| 本地连接/写失败/EOF/超时/取消 | **未知** | 向 worker 读一次 `stats`，比对它实际的运行期预算 |
| └ 读到「已在新额度」 | 已应用 | 保存设置，释放承诺，按成功返回（`applied.settled_after_lost_reply`） |
| └ 读到「还在旧额度」 | 没有应用 | 释放承诺，409（原设置与 worker 一致） |
| └ 读不到 / 报第三个数 | 仍未确认 | **保留承诺并标记未确认**，返回 **503** |
| 保存设置失败 | worker 已应用、文件没存 | 把 worker 回滚到原额度 |
| └ 回滚被 worker 确认 | 已回到旧额度 | 释放记录，返回 **500** |
| └ 回滚被拒绝 / 答复丢失 / 读不到 / 取消 | worker 可能还在新额度 | 保留**原请求**并标记未确认（`phase` 记录回滚阶段），返回 **503** |

#### 操作记录与预算字节是两回事（第二轮验收，MYS-2801）

第一版把「这次操作要预留多少字节」当成了「这次操作的状态」，于是**预留为零的操作没有记录**：
减额、改成同样的值、`CV84X6_NPU_RESERVE_MB=0`、以及辅助模型（没有运行期预算）都走
`admit_limit_raise` 返回 `None` 的分支，`configure` 的答复一丢就没有任何东西可以核对，
代码在空值上解引用，HTTP 500、保存 1000、worker 400、账本为空。

现在 `BudgetPromise` 的两个职责分开，`bytes` 可以为 0：

| 字段 | 含义 |
|---|---|
| `bytes` | 这次操作预留的设备字节；减额/同值/关闭 reserve/辅助模型都是 **0** |
| `pending_limit_bytes` / `previous_limit_bytes` | 这次操作要改成什么、原来是什么（都是内存上限字节，`null` 也折算成同一个数） |
| `phase` | 走到哪一步：`sent` / `settling` / `rollback_sent` / `rollback_unknown` / `rollback_refused` / `rollback_failed` |
| `unresolved` | 结果是否已知；和 `phase` 互补，前者说「知不知道」，后者说「试过什么」 |

零字节的 `bytes` 只影响准入算术（它不占额度），不影响状态机：核对用的是
`pending_limit_bytes`，冲突判断用的是记录本身，所以零字节操作和 600 MiB 操作走**同一条**
收尾路径，没有第二套分支。

**记录在第一个可能被取消的 await 之前就存在。** 第一版只在 `configure` 周围的取消处理里
标记，于是「超时 → 核对中取消」这条路径留下 `pending 1 / unresolved 0`：内存被占着，却
没有任何东西说它可疑，后续一个**不同**的变更就能压在它上面（复现里返回 200、残留 600 MiB
承诺），而卸载之后记录还在。现在进入事务就登记，核对 / 持久化 / 回滚的每一个 await 处取消
都会命中已标记的记录。

**回滚失败不改写原请求。** 第一版把 `pending`/`previous` 都覆盖成旧额度，于是唯一描述
「操作员要什么」的东西没了：重试原额度 409（不算同一次请求）、重试旧额度 503。现在记录
保留原请求，`phase` 单独说回滚到了哪一步；回滚没有被确认时返回 **503**（不宣称已恢复），
磁盘恢复后重试原请求就能核对并落盘。

**卸载确认退出后清掉该 worker 的全部操作记录**，不只是未确认子集——记录描述的是「发给
那个进程的东西」，进程没了就没有任何东西还能核对或重试它。

未确认的承诺会**继续占着额度**，后续加载与增额都不能再花这部分内存。它能被三条真实路径清掉
（都不需要重启进程）:

| 路径 | 做什么 | 结果 |
|---|---|---|
| 重试**同一次**保存 | 生命周期锁内先 `stats` 核对，再决定收敛方向 | 已应用：补写设置、交接承诺、200；仍在旧额度：释放、409；读不到：503 并继续保留 |
| 保存**不同**的额度 | 未确认时受控拒绝 | 409 `model_busy`，提示先重试上一次保存 |
| 卸载且**进程确认退出** | `_forget` 里清掉该模型的未确认承诺 | 承诺归零；进程还在（存活/卸载失败）则保留 |

承诺里同时记着这次操作**想改成什么**（`pending_limit_bytes`）和**原来是哪个**
（`previous_limit_bytes`），所以核对、重试和后台收尾都不需要当初那个 HTTP 请求还在。
取消时先同步标记未确认，再在**同一次请求的生命周期锁内**做一次有界核对：不留下脱离锁继续
写设置的后台任务；二次取消或核对失败就停在未确认状态（保守，不宣称已恢复）。

#### 锁与顺序

| 锁 | 保护什么 | 持有多久 |
|---|---|---|
| 每模型的生命周期锁（`lock_for`） | 该模型的加载/卸载与设置更新互斥 | 整段设置更新（核对 + `configure` 的 10 s 上限 + 持久化） |
| 设备预算锁（`_budget_lock`） | 「读堆 → 检查 → 登记承诺」 | 只有这一段，中间没有 await，**不含**任何加载或 RPC |

顺序固定为**生命周期锁 → 预算锁**，从不反向获取。加载路径只取预算锁，而且**不**跨
spawn 持有它——所以不同模型仍然并行加载（`test_models.py` 的并行用例保留），同模型的重复
加载仍然合并。

设置更新在拿到生命周期锁之后**重新读一遍状态和旧配置**：这次请求可能排在一次加载后面等了
几十秒，`operation` 和已存设置都可能已经变了。核对上一次未确认操作、增额检查、worker
确认、持久化是一个事务，全在锁内完成：承诺在检查通过时登记，`configure` 成功且新设置写入
store 之后才交接。加载路径相反：spawn 失败、worker 未就绪、能力探测失败、被取消，一律释放。

显式值与 `null`（恢复默认）走**同一条**路径：`null` 先算出推算默认值，再和显式值一样做增额
判断。尚未加载的模型只保存设置，加载时再准入。

### 前缀缓存只受本模型的上限约束（v0.6.34 起，MYS-2785）

v0.6.32 及以前有两个上限同时在管同一件事：

| 上限 | 来源 | 传给 worker |
|---|---|---|
| `prefix_cache_max_mb`（默认 2048 MiB） | 全局设置项 | `--device-kv-budget-mb` → 缓存自己的 `max_bytes` |
| 本模型运行期预算 `上限 − 静态` | 每个模型的内存上限 | 调度器对「会话 + 缓存」之和的限额 |

于是「这个模型最多占多少内存」答不出来：上限只留下 300 MiB 运行期预算的模型，缓存照样
可以涨到 2 GiB，直到调度器在插入前把它压回去。

**v0.6.34 起只剩一个上限**：缓存的 `max_bytes` = 该模型的运行期预算 = `上限 − 静态`
（再被设备余量截断）。于是可以算：

```
一个模型的前缀缓存上限 = 上限 − 静态
一个模型最多占用的设备内存 = 它的内存上限
整板最多占用             = 已加载模型的内存上限之和
```

三条都是**上限**：会话与缓存共用同一份运行期预算，缓存是弹性的一侧
（`Scheduler._fits` 与 `_cache_room_for` 在准入前和插入前都先淘汰缓存）。

> **「预留」是覆盖分配峰值的保守上界，不是与最终常驻逐字节相等。** 调度器预留的是
> 「引擎在这一步可能同时占住的最大字节」，它通常**大于**会话跑完之后的常驻占用：
> park 缓冲按 4096 槽取整、扩容时旧缓冲和新缓冲会同时在世。用 `kv_used_bytes`
> （按 token 长度估算，不含 park 容量取整）去和 `reservation()`（峰值上界）比较，看到的差不是记账错误。

### 预留上界怎么算（覆盖分配峰值）

`ensure_park`（`native/src/llm_engine.cpp`）的三条规则决定了上界：

1. 容量按 `kParkGranule = 4096` 取整，**不是**按 token 数；
2. 增长时新容量是 `max(need, cap + cap/2)` 再取整（至少 1.5 倍），所以容量序列是
   `4096 → 8192 → 12288 → 20480 → …`；长 prompt 也可能直接跳过中间档；
3. 扩容先分配新缓冲、拷贝、**再**释放旧缓冲——**峰值是 `old + new` 同时占住**。

因此预留不能只看「最终长度」，必须覆盖**所有可能的增长历史**。`_parked_slots()`
取的是上界而不是某一条轨迹：增长前 `old_cap` 必然是严格小于目标长度的粒度整数倍
（被上下文封顶的缓冲不会再次增长），它可能取到的最大值就是「目标长度下方最后一个
粒度倍数」；`new_cap` 与 `old + new` 都随 `old_cap` 与 `need` 单调增，所以取这两个
最大值即可覆盖所有历史，包括跳过的中间长度。

| 场景（granule=4096） | 实际同时占住 | `_parked_slots()` |
|---|---|---|
| 首次到 4096 | 4096 | 4096 |
| 首park 4096，再长到 **4097** | 4096 + 8192 = **12288** | 12288 |
| 4096 → 8193 | 4096 + 12288 = 16384 | 20480 |
| 4096 → 8193 → 12289 | 12288 + 20480 = 32768 | 32768 |

★ 上一版（`5cedd6c`）在这里错过一次：它首次循环就把容量设成最终长度再退出，等于假设
「一次分配到位」，于是 4096→4097 只预留 8192 槽、实际峰值 12288 槽——9B（32 KiB/token）
上少算 **128 MiB**。当前实现（`d774dfa`）改用上面的上界；`tests/test_cache_in_model_limit.py`
用参数化的增长轨迹 + 小上下文下穷举全部分配历史两种方式验证。

另外两处也得算进去：

| 分配 | 引擎里的位置 | 量级（9B，32 KiB/token） |
|---|---|---|
| **快照带整份线性状态**：`Session::snapshot` 对每个线性层分配整块 `state_a + state_b`，与 prefix 长短无关 | `Session::snapshot` | **25.5 MiB/条目**（`_snapshot_bytes()` 已计入 `linear_state_bytes`） |
| park 粒度取整本身 | `ensure_park` | 一段 2835 token 的会话按 4096 槽算，比 raw token 多 **39 MiB/会话** |

这两处**不是**「引擎的临时工作区无法建模」——是可以精确算出来的常数量，所以修在记账里，
而不是在文档里让操作员多留 0.5 GiB。

### 实测（`.157`，Qwen3.5-9B-128k，静态 13331 MiB，上限 = 静态 + 1024 MiB）

两组证据分别验证 HTTP 并发和原生扩容，不能互相替代。

| 场景 | 峰值 NPU | 上限 | 结论 |
|---|---|---|---|
| HTTP 基线 `ad8f192`（v0.6.33），缓存填充后两路请求 | 14430 MiB | 14355 MiB | 超 75 MiB |
| HTTP 候选 `d774dfa`，同样参数 | 14338 MiB | 14355 MiB | 采样未超限 |
| 负责人原生复测（`12c1182` 的调度器） | 14349 MiB | 14355 MiB | 427 个采样点未超限 |

原生复测使用 `tools/mys2785_cross_granule.py`，直接驱动真实 Scheduler 和 NativeBackend：

- 22 次请求将缓存填到 832.5 MiB，已发生 7 次淘汰；
- 两路 6144-token 请求在同一个存活的原生会话中从 4096 继续预填充到 6080，
  原生诊断日志分别记录 `need=6080 old=4096 new=8192`；
- 120 秒提交窗口内，6 路交替提交，27 次取消确实由调度器完成，27 次正常完成；
- 无请求失败或 worker fault，NPU 最小余量 12275 MiB；释放后占用归零，原服务恢复。

诊断库只在 `ensure_park` 增加分配轨迹日志，不随安装包发布。原始 JSON、日志和诊断补丁
附在 MYS-2293 验收评论。采样不能证明两次读数之间没有瞬时峰值；瞬时分配上界由
`test_cache_in_model_limit.py` 的已知增长路径、上下文封顶和小上下文穷举测试补充验证。

之前交付把两次 HTTP 请求称为“同一原生会话跨粒度”，这是无效证据：每次 HTTP 请求
都会新建、关闭原生会话。旧压力脚本误用 `data ` 匹配 SSE 的 `data:`，也没有真正取消。
两个脚本现已修正，取消必须发生在未结束的内容流中；错误、无效采样和缺少并发均返回非零。

**算例**（`.157`，35B-A3B 128k，静态 22752 MiB，`max_concurrent_per_model=2`）：

| 操作员设的上限 | 运行期预算 | 缓存最多占 | 该模型最多占 | 说明 |
|---|---|---|---|---|
| 默认（推算 23232 MiB） | 480 MiB | 480 MiB | 23232 MiB | 一路会话**预留** 112 MiB（线性状态 31.9 + 20 KiB×**4096 槽**，不是 2560 token）；两路 224 MiB 时缓存最多 256 MiB |
| 静态 + 1024 MiB = 23776 MiB | 1024 MiB | 1024 MiB | 23776 MiB | 两路会话 224 MiB，缓存最多 800 MiB；比默认多出的 544 MiB 全部给缓存 |
| 静态 + 0 = 22752 MiB | 0 | 0 | 22752 MiB | 缓存关闭，且只允许单路会话 |

整板：以上三条任选其一，再叠上其余已加载模型各自的上限即得整板上限；6 个模型全部加载
时是各自上限之和（见下面「本版本各模型的实际数值」）。**35B 的默认上限已经贴着 1 GiB
的 NPU 下限**（MYS-2784），所以默认值里没有额外给缓存留空间——想要更大的缓存，就调大
那个模型的上限，不要指望全局设置（它已经没有了）。

### 全局 `prefix_cache_max_mb` 已删除，旧客户端不会报错

- 状态文件里的旧值**读入后忽略**（`LEGACY_SETTING_FIELDS`），且下次 `save` 不再写回；
- `GET /api/settings` **不再返回**这个字段；
- `POST /api/settings` 里**仍然接受**它，返回 200 但完全不生效。这是刻意的：v0.6.32 的
  控制台保存设置时会 POST 整个表单，改成 422 会让升级后每一次保存都失败。
- `prefix_cache_entries`（条目数）与 `prefix_cache_ttl_min`（保留时间）**不变**。
- worker 的缓存开关：**关缓存是一个操作员指令，优先于任何推算出来的预算**。
  两种写法等价：新加的 `--no-prefix-cache`，以及旧的 `--device-kv-budget-mb 0`
  （A/B 脚本原来就靠它）。它们在有 bm-smi 读数、没有读数、有模型上限三种情况下都生效。
  `tools/decode_quantum_ab.py` / `decode_quantum_smoke.py` 已迁到 `--no-prefix-cache`。

  > 第一次交付在这一点上做错了：当时把 `--device-kv-budget-mb` 当成「兜底」，优先级
  > 排在 bm-smi 读数**之后**，于是要求关缓存的 A/B 脚本拿到了设备余量（8000 MiB）。
  > 「关」是一个决定，设备读数是一个推断，两者冲突时决定优先。非零的
  > `--device-kv-budget-mb` 则是 `min`：它只能压低上限，**永远不能把缓存抬到模型上限
  > 之上**——这正是本任务的目的。

### 改小到低于当前占用 → 400

模型已加载时把上限设成比它**当前占用**还小，返回 400 并列出分解：

```
模型 X 当前占用 2605 MiB（静态 2605 MiB + 运行期 0 MiB），
不能把上限改为更小的 512 MiB；请先卸载该模型，或把上限设到不低于当前占用
```

不悄悄卸载它，是因为「保存设置」杀掉一个正在服务的模型是操作员没有要求的动作；
要卸载有专门的按钮。上限**等于**当前占用是允许的（边界值合法）。

### 默认上限的推算

```
默认上限 = round_up_64MiB( 静态占用 + 运行期额度 )

运行期额度 = (1 + 10%) ×
    chat / ocr_vl:  (线性状态 + 每 token KV × (默认提示 + 默认补全)) × 并发数
                    + 256 MiB（一份前缀缓存的经验值）
    其他 kind:      该类的工作缓冲实测值
```

**这条推算没有因为删除全局缓存上限而改**（MYS-2785）。那 256 MiB 现在是「默认上限里
给缓存留多少」这一**策略**值，不再是任何设置项的副本；它和运行期预算是同一份预算的两
个用途，所以调大模型上限就是调大缓存空间。不给默认值额外加空间，是因为 24 GiB 板上
35B 的余量已经贴着 1 GiB 的 NPU 下限（MYS-2784）：向上加 256 MiB 会把默认上限推到下限
之上，默认配置反而不能加载。需要更大缓存的用户把那个模型的上限调大即可。

取值理由，逐项：

- **默认提示 2048 token、默认补全 512 token**，不是 `context_length`。按 128k 预算
  KV 会推出「默认上限 30 GiB」这种没人需要、也没人能用满的数，操作员的第一反应只会
  是把它调大——默认值就失去了意义。2048 是一次对话（system prompt + 几轮）实际占用
  的长度，也是小模型的全部上下文。长提示由调度器按**设备剩余内存**准入，那才是随上下文
  伸缩的检查。
- **并发数**取 `max_concurrent_per_model`，因为额外的会话确实要多占那么多内存。
- **每 token KV 20 KiB、线性状态 31.9 MiB**，这是 `.155` 上从
  `llm_engine_kv_bytes_per_token` / `llm_engine_linear_state_bytes` **读出来的**，
  不是按「35B bf16」推算的。Qwen3.5/3.6-A3B 是 40 层里只有 10 层全注意力，所以每 token
  只是 10 × 1 KiB × 2 = 20 KiB；按 2 MiB/token 猜会把默认值放大两个数量级。
- **10% 余量**：实测峰值与估算相差在 3% 以内，10% 覆盖堆内碎片对齐、图像请求时视觉塔的
  临时缓冲、分词器在宿主侧的缓冲。
- **向上取整到 64 MiB**：一个「7943 MiB」的上限读不出是测量还是巧合，而这个余量本来
  也不知道到 1 MiB。

### 静态占用为什么用实测而不是 `bmrt_get_bmodel_info`

`bmrt_get_bmodel_info` 的 `io_mem` 是**每个网络每个 stage 的 `io_size` 之和**，
对 dynamic / history 的 build 严重高估。`.155` 实测（2026-11-07）：

| 模型 | 文件 | bmrt: coeff+neuron+instr | bmrt: io | 加载后实测 |
|---|---|---|---|---|
| qwen3.6-35b-a3b-128k | 19683 MiB | 20122 MiB | **17971 MiB** | **22752 MiB** |
| qwen3-embedding-0.6b（seq2048，默认档） | 1173 MiB | 1276 MiB | 225 MiB | **1465 MiB** |
| qwen3-embedding-0.6b-seq512（短文本档） | 1150 MiB | 未采 | 未采 | **1217 MiB** |
| qwen3-embedding-0.6b（seq8192，旧） | 1294 MiB | 2266 MiB | 897 MiB | 2605 MiB |
| qwen3-asr-0.6b | 1515 MiB | 1531 MiB | 113 MiB | 1639 MiB |
| bge-reranker-v2-m3 | 1092 MiB | 1165 MiB | 0 MiB | 1136 MiB |
| ppocrv6-medium（det+3rec+layout） | 241 MiB | 186 MiB | 0 MiB | 154 MiB |

embedding 的三行是 MYS-2696 / MYS-2706 在 `.157` 上用设备堆差值实测的（`tools/embed/mem_probe.py`、
`tools/embed/seq512_bench.py`）：seq2048 静态 1465 MiB，比 seq8192 少 1140 MiB，估算值与实测
差 −13%，仍在上面那条区间内。短文本档 seq512 为 1217 MiB，比 seq2048 少 248 MiB ——
**省的主要是激活/IO，权重不变**。bmodel 文件的 `bmrt` 三列没有为 seq512 单独采（它的
结论只用于估算，而估算值会被第一次加载的实测值替代），文件大小为实测值。

把 `io_mem` 算进去会给 35B 推出 55 GiB 的默认上限——比整块板（34 GiB）还大。所以：

- **估算**（从未加载过）只取 coeff + neuron + 指令，落在实测的 −13%..+2% 之内；
- **实测**（本进程加载过一次）取设备堆差值，直接替代估算值。

实测有可能把别人的分配算进来（同一窗口里还有别的 worker 在装载），所以只在
`0 < 差值 <= 2×文件大小 + 512 MiB` 时才采纳，否则退回估算——误判的代价只是回到估算，
不会拒绝一次加载。

**默认值用的是加载时检查用的同一个静态值**，所以默认上限永远不可能拒绝一次加载。
这是刻意的：静态值在第一次加载前是估算，之后变成实测，默认值随之移动一次然后稳定。

| ppocrv6-medium | ocr | 154 MiB | 176 MiB | **384 MiB** |

设备总容量 NPU 30720 MiB + VPP 4094 MiB = 34814 MiB。五个模型同载需
22752+1600+1344+1856+384 ≈ 27.4 GiB（默认上限之和，含各自的运行期余量），
比 seq8192 时代省 1.1 GiB。实测五者同载合计 27620 MiB（`docs/device-memory.md`，seq8192 时），
同样在容量之内；embedding 换成 seq2048 后那一项再降约 1.1 GiB。

**短文本档不需要改任何设置**：它的静态占用更小（1217 MiB），推算出的默认上限因此比
seq2048 那条低（1217 + 106 → 取整 **1344 MiB** 对 1600 MiB，两者都按 `default_limit_bytes`
算），两档都在容量内。

★ **两档同时在住，按两者之和算：约 2682 MiB（1465 + 1217）**。服务里每个模型是独立的
worker 进程，设备内存不跨进程共享。`tools/embed/seq512_bench.py` 在**同一进程**里先后
`cv_embed_create` 两档时测到合计 2372.1 MiB（后加载的只 +907.6 MiB），那是同一进程内运行时
复用了权重，**不代表服务里的部署形态**，不要用它估算两档同时在住的占用。控制台的
「默认上限之和」按两个独立 worker 各算一条上限，与部署形态一致。

## 三、接口（只增不改）

`GET /api/models` 与 `GET /api/stats` 的每个模型新增：

```jsonc
{
  "settings": {                      // 操作员存下的原始值，含 null
    "idle_unload_min": 1,
    "auto_load": null,
    "mem_limit_mb": 2048
  },
  "effective": {                     // 此刻真正生效的
    "idle_unload_min": 1,
    "auto_load": true,
    "mem_limit_bytes": 2147483648
  },
  "mem_limit_default_bytes": 2752 * 1048576,   // 推算的默认上限
  "mem_static_bytes": 2605 * 1048576,          // 静态占用
  "mem_used_bytes": null                        // 已加载时为实时值
}
```

新增两条路由：

| 路由 | 说明 |
|---|---|
| `GET /api/models/{id}/settings` | 上面那些字段 + `limits`（字段上下界）+ `auto_load_note` |
| `PUT /api/models/{id}/settings` | 改设置；只传要改的字段，传 `null` 恢复默认 |

`PUT` 的规则：

- **省略**某字段 = 不动它；传 `null` = 恢复默认；两者语义不同，靠 pydantic 的
  `model_fields_set` 区分；
- 越界**拒绝**（400）而不是钳制，和 `/api/settings` 相反。理由：内存上限是操作员用来
  保护板子的数，静默把 0 当成「32 MiB」正好让它失效；而空闲分钟数在设置页是个 spinner，
  陈旧值不该让保存失败；
- 模型正在加载/卸载时 409——上限在 spawn 时读取，这时改哪一边都落不到实处；
- 改小到低于当前占用 400（见上）。

返回体里的 `applied` 是运行中 worker 的回答（`kv_budget_bytes` 等），或者一个带
`error` 的对象。worker 不在（正在卸载、刚死掉）时是 `null`，这不算保存失败——上限
存在 state 里，下一次加载自然会读到。

`applied` 里与本任务相关的三个数（都在 worker 的 `stats` 里同名出现）：

| 字段 | 含义 |
|---|---|
| `mem_runtime_budget_bytes` | 本模型上限折出来的预算 = `上限 − 静态`；未设上限时为 `null` |
| `device_budget_bytes` | 加载后 bm-smi 看到的余量减 NPU 下限；无可读读数时为 `null` |
| `kv_budget_bytes` | 上面两者的较小值，调度器准入与缓存上限都用它 |

## 四、mock

mock 后端的字段与板上完全一致，界面可以完全离线开发：

- 静态占用 = 各 `.bmodel` 文件大小之和（没有 libbmrt，走文件大小回退）；
- `mem_used_bytes` = 静态 + mock 调度器上报的 `kv_used_bytes`；
- `effective` / 默认上限的算法与板上同一份代码。

## 五、升级

老 state 文件里没有 `model_settings`，读出来就是空表，每个模型都跟随默认值——也就是
MYS-2675 之前的行为。不需要迁移步骤，也不需要写一次文件。手工编辑过、字段值非法的
条目会**逐字段**退化成 `null`（跟随默认），而不是让服务启动失败。
