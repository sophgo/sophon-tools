# 64 对齐下低余数 prompt 的正确率与精确尾部修复评测（10.42.0.242，Qwen3.6-35B-A3B 32k）

| 项目 | 内容 |
|---|---|
| **历史结论** | 64 对齐下 `n % 64 ≤ 7` 的短 prompt 已经在出错（35/40），形态是第一个 token 进 `<think>` 后耗尽预算、答案没写出来；补 16 行精确回放修到 **39/40** |
| **当前约束** | 短 prompt 精确计算最后 min(设置值, 16) 个 token，见 `docs/DESIGN.md` §3.4；预填充头仍按 64 对齐 |
| **本篇保留** | 失败用例原文与复跑、机制说明、首字代价表——v0.6.5 的直接依据 |

MYS-2403，接 MYS-2396（`prefill-ab-eval.md`，PR #23）。2396 的用例特意挑了 `n % 64 >= 16`，
所以 64 规则下每条 prompt 至少有 16 行走精确 decode 回放。本阶段回答两个问题：

- **Q1**：当 `n % 64` 只有 0–7 时（精确回放几乎为零），当前产品行为是否已经有正确率问题？
- **Q2**：引擎已有的 `llm_session_set_exact_tail`（强制末尾 K 行精确回放）能否修好它，首字代价多少？

本阶段只做评测，**不改引擎、不改 app、不发版**。

**结论先行**

1. **Q1 成立：64 对齐下低余数 prompt 已经在出错，40 条里 5 条失败（35/40）。** 失败全部在 A 类
   短问答（A 10/15），形态是**不答**：第一个 token 进 `<think>` 后把推理过程当正文写，64 token
   预算耗尽，答案一个字都没写出来。B 类长文抽取 15/15、C 类多轮追问 10/10 全通过。
   - 对照 2396：同一批题在 `mid` 集（`n%64 >= 16`）下 64 规则 40/40 全通过。**差异只在精确尾部宽度**。
2. **Q2 成立但代价极大：`--exact-tail 16` 把 5 条失败全部修好（39/40），但首字时间翻倍。**
   - 正确率 35/40 → 39/40：A 类 10/15 → **15/15**；但 C 类 c03 从通过变失败（答成 `Aveline`，
     漏了姓氏 `Roth`），所以不是 40/40。
   - TTFT 中位数 **0.936 → 1.917 s（+0.98 s，2.05×）**。分类：A +0.79 s（1.99×）、B +1.22 s（1.64×）、
     C +0.77 s（2.03×）。**这个代价是 2396 里「对齐放宽」全部收益（-0.48 s）的两倍以上。**
3. **精确尾部对已通过的用例没有副作用：R3（`mid` 集 + `--exact-tail 16`）40/40 通过，40 条 token
   全部逐位与 2396 的 64 基线相同，TTFT 差值中位数 +0.0002 s，区间 [-0.024, +0.0064]。** 原因是
   `mid` 集在 64 规则下本来就已经回放了 ≥16 行，设 16 等于没设 —— 这正好证明该开关只在「回放不足
   16 行」时才改变行为，不会误伤现状。
4. **落地判断：这个修复在现产品里用不上。** `app/engine/scheduler.py:369` 只对 ≥2048 token 的
   prompt 启用精确尾部（`EXACT_TAIL_MIN_PROMPT = 2048`），而本次失败的 prompt 是 64–128 token。
   想用它，要么把阈值降下来（代价见表 2），要么换别的修法。
5. **失败与题面难度无关，只与「是否开始作答」有关。** 修复后模型答的答案与 64 宽尾部一致
   （`210`、`Shakespeare`、`Canberra`、`100`、`8` 全部正确），说明偏差打在「要不要开口」，
   不是「算得对不对」—— 与 2396 对因果的判断一致。

## 方法

### 新用例集 `low`（`tools/prefill_ab_cases/low/`）

40 条，题目、题型、判分正则与 2396 的 `mid` 集**完全相同**，只重新调整填充句子使长度落进新窗口：

| 类型 | 数量 | 约束（生成器 `--verify` 校验） | 实测 |
|---|---:|---|---|
| A 短问答 | 15 | `n >= 64` 且 `n % 64 <= 7` | 64–128 token，余数 0–5 |
| B 文中抽取 | 15 | `n >= 64` 且 `n % 64 <= 7` | 320–452 token，余数 0–7 |
| C 多轮追问 | 10 | 历史 ≤ 2048；追问 64–71 token（即 `delta % 64 <= 7`） | 历史 201–238，追问 64–70 |

仍在约束内用**整句追加**调长度（`A_QUESTION_PAD` / `GENERIC_PAD` + 新增的 `SHORT_PAD`），
全部是真实英文散文，**没有合成 id**。`mid` 集的 40 个 id 文件与 `cases.json` **逐字节未变**
（`--verify` 通过，git 里无改动）。

C 类的历史与追问照旧从同一次三消息渲染里切出来，assistant 轮次走生产模板（`render_messages`，
thinking 关闭），追问块 = 模板为下一轮追加的那段。low 集的追问比 mid 长（64–70 vs 32–36），
所以历史略短（201–238 vs 221–272），两者都在 2048 以内。

### 评测脚本

`tools/prefill_ab_eval.py` 新增 `--exact-tail K`（默认 0，即引擎原行为）：

- A/B 类：在**评分用的那次** `prefill` 前调 `llm_session_set_exact_tail(sess, K)`；
- C 类：只在**追问的那次 `extend`** 前调，**不作用于历史 prefill**（与产品
  `app/engine/scheduler.py:369` 的位置一致）。理由：该开关本身只对下一次 feed 生效
  （`native/src/llm_engine.cpp:1039-1040` 调用后清零），C 类的首字时间是 extend 的耗时，
  把历史也改成精确回放既不符合产品行为，也会把 TTFT 摊到错误的地方。
- 输出 JSON 记录 `exact_tail`，与 `align` 并列，避免运行结果被误标。

其余（一进程加载一次模型、每条新会话、greedy 64 token、判分、300 s 看门狗、外层 `timeout 3600`）
与 2396 相同。

### 执行（每轮一个进程，顺序执行，每轮后查 `dmesg`）

```
LLM_PREFILL_ALIGN=64 python3 tools/prefill_ab_eval.py \
  --lib /opt/sophgo/cv84x6_llm_server/lib/libcv84x6_llm.so \
  --model /data/cv84x6_llm_server/models/qwen3.6-35b-32k/model.bmodel \
  --cases tools/prefill_ab_cases/low/cases.json --out logs/low-align64-tail0.json --dev 0
# R2: 同上，--exact-tail 16
# R3: --cases tools/prefill_ab_cases/cases.json（mid 集）--exact-tail 16
```

原始 JSON 提交在 `tools/prefill_ab_cases/logs/`：`low-align64-tail0.json`、`low-align64-tail16.json`、
`mid-align64-tail16.json`，以及复跑 `low-recheck-tail0.json`、`low-recheck-tail16.json`。

## 结果

### 汇总

| 轮 | 用例集 | align | exact_tail | A | B | C | 总体 | TTFT 中位数 |
|---|---|---:|---:|---:|---:|---:|---:|---:|
| R1 | low | 64 | 0 | 10/15 | 15/15 | 10/10 | **35/40** | **0.936 s** |
| R2 | low | 64 | 16 | **15/15** | 15/15 | 9/10 | **39/40** | **1.917 s** |
| R3 | mid | 64 | 16 | 15/15 | 15/15 | 10/10 | **40/40** | 1.327 s |
| 2396 基线 | mid | 64 | 0 | 15/15 | 15/15 | 10/10 | 40/40 | 1.326 s |

### 表 1：精确尾部的正确率效果（R1 → R2，low 集）

- **修好 5 条**：a01、a07、a08、a12、a15 —— R1 全部是「`<think>` 里写推理、预算耗尽」，
  R2 全部变成 `\n\n<think>\n\n</think>\n\n<正确答案>`，答案正确（`210` / `Shakespeare` /
  `Canberra` / `100` / `8`）。
- **弄坏 1 条**：c03 —— R1 答 `Dr Aveline Roth`（通过，判分正则 `Roth`）；R2 答 `Aveline`
  （漏姓氏，不通过）。**这不是拒答，是答不完整**，形态与 R1 的 5 条不同。
- **17/40 条 token 流逐位相同**，其余 23 条有分叉 —— 说明 `exact_tail=16` 只在「回放不足 16 行」
  的地方改变状态，其余位置是恒等的。

### 表 2：精确尾部的首字代价（R1 → R2，low 集）

| 分类 | TTFT 中位数 R1 (s) | TTFT 中位数 R2 (s) | 倍数 | Δ 中位数 | Δ 区间 |
|---|---:|---:|---:|---:|---|
| A 短问答（15） | 0.7997 | 1.5877 | **1.99×** | **+0.7892** | [+0.7762, +1.1898] |
| B 文中抽取（15） | 1.9112 | 3.1322 | **1.64×** | **+1.2205** | [+1.2097, +1.2441] |
| C 多轮追问（10） | 0.7494 | 1.5236 | **2.03×** | **+0.7718** | [+0.7668, +0.7828] |
| **总体（40）** | **0.9359** | **1.9167** | **2.05×** | **+0.9808** | [+0.7668, +1.2441] |

代价的物理来源可以在 `a06`（n=128，余数 0）上直接算出来：R1 是 128 行预填充 + 0 行回放（1.014 s），
R2 是 64 行预填充 + 64 行精确回放（2.203 s）——**多了 64 次逐行 decode，净增 1.19 s，约 18.6 ms/行**。
短 prompt（n=67）同样多回放 64 行，但注意力更短，净增 0.79 s ≈ 12.3 ms/行。**代价与「补回放的行数」
成正比，而低余数 prompt 恰恰需要补最多（最多 64 行）。**

对照 2396：把对齐从 64 放宽到 16 的全部收益是中位数 -0.48 s（-36%）。
**用精确尾部去修低余数的正确率问题，代价（+0.98 s）是那笔收益的两倍。**

### 表 3：精确尾部对已通过用例的副作用（R3 vs 2396 基线，mid 集）

| 分类 | 通过 | token 全等 | TTFT 基线 (s) | TTFT R3 (s) | Δ 中位数 | Δ 区间 |
|---|---:|---:|---:|---:|---:|---|
| A（15） | 15/15 | **15/15** | 1.2803 | 1.2794 | -0.0009 | [-0.0073, +0.0064] |
| B（15） | 15/15 | **15/15** | 2.7150 | 2.7180 | +0.0009 | [-0.0240, +0.0030] |
| C（10） | 10/10 | **10/10** | 0.8005 | 0.7996 | -0.0006 | [-0.0056, +0.0025] |
| **总体（40）** | **40/40** | **40/40** | **1.3264** | **1.3274** | **+0.0002** | **[-0.0240, +0.0064]** |

**40 条 token 流与 2396 的 64 基线逐位完全相同，TTFT 差值在噪声范围内。**
原因是机制性的：`mid` 集保证 `n%64 >= 16`，64 规则本来就已经把 ≥16 行送精确图
（A/B 类回放 `n%64` 行；C 类追问 16–63 token < 64，整块回放），所以再要求「末尾 16 行精确」
是幂等的 —— `exact_from = n - min(n, max(0, 16))` 落不到任何已对齐块的边界之内
（`native/src/llm_engine.cpp:1047`）。

**这条数据本身就是 Q2 的边界条件**：该开关只在「原本回放不足 16 行」时改变行为，
在现状（回放充足）下是零成本零影响 —— 它不会误伤，但也只在低余数那一角才有意义。

## 失败用例原文与复跑

## 为什么低余数会出事：机制说明

`native/src/llm_engine.cpp:1039-1047`：

```cpp
const int exact_from = n - std::min(n, std::max(0, s->exact_tail));
s->exact_tail = 0;
...
int L = cur;
if (e->is_dynamic && cur > align_above() && cur % al != 0)  L = (cur / al) * al;
if (c0 + L > exact_from) L = std::max(0, (exact_from - c0) / al * al);
```

64 规则下，`exact_tail = 0` 时 `exact_from = n`，所以前 `n - n%64` 行走**预填充图**、
末尾 `n%64` 行走**精确 decode 回放**。厂商预填充图的 routed-expert MoE 在 CV84X6 上不精确
（第 0 层余弦 0.75，`tools/precision/README.md`），decode 图是精确的。

因此**精确回放的行数就是 `n % 64`**：

- `mid` 集（2396）：`n%64 >= 16`，至少 16 行精确 —— 40/40 全通过。
- `low` 集（本阶段）：`n%64 <= 7`，几乎全走近似图 —— 35/40。

同一批题、同一台设备、同一个库、同一个模型，**唯一变量是精确尾部的宽度**，通过率从 40/40 掉到
35/40。这不是「相关性」，是把变量单独拿掉后的直接对照。

`--exact-tail 16` 的作用是把 `exact_from` 压到 `n-16`，于是 `L` 被向下取整到
`((n-16)/64)*64` —— 对 `n=67` 是 `(51/64)*64 = 0`，即**整段 67 行全部精确回放**；
对 `n=128` 是 `(112/64)*64 = 64`，即 64 行预填充 + 64 行回放。这正是表 2 里
「代价与补回放的行数成正比」的来源。

## 结论与建议

### Q1：低余数 prompt 现在就在出错

**是。** `n % 64 = 0..7` 时，64 规则只回放 0–7 行，40 条里 5 条（12.5%）从「正常作答」变成
「把推理当正文写、预算耗尽不答」。同一批题在 2396 的 `mid` 集（`n%64 >= 16`）下 40/40 全通过。

- 失败集中在 **A 类短问答（5/15 = 33%）**，B 类长文抽取和 C 类多轮追问在低余数下**没有复现失败**
  （15/15、10/10）。这与 2396 的失败分布（A 1 条、B 1 条、C 3 条）不同，说明哪一类先崩取决于题面，
  但「低余数 → 更容易不答」这个方向在 A 类上是清楚且可复现的。
- 真实产品里，prompt 长度落在 64 倍数附近是很常见的事（用户问句长度连续分布，约 1/8 的 prompt
  会落在 `n%64 <= 7`）。**这是当前线上就存在的、可被复现的正确率缺口，不是理论风险。**

### Q2：精确尾部能修，但代价大于收益

**能修，但代价是首字时间翻倍。**

| | 正确率 | TTFT 中位数 |
|---|---|---|
| R1（现状） | 35/40 | 0.936 s |
| R2（`exact_tail=16`） | 39/40 | 1.917 s（**+105%**） |

- 修好 5 条不答，但引入 1 条答不完整（c03），所以是 39/40 不是 40/40 —— **是部分修复**。
- 代价 +0.98 s，是 2396 里「对齐放宽」全部收益（-0.48 s）的两倍以上。**用它去换对齐放宽不划算**，
  两者不能互相抵消。
- 对已通过的用例（`mid` 集）零影响：R3 40/40、40 条 token 逐位全等、TTFT 差值中位数 +0.0002 s。
  这是好事（不会误伤），但也说明它只在低余数那一角起作用。

### 落地建议（按证据分档）

1. **不要用「全局降阈值 + 精确尾部」的方案。** 代价 +105% 首字，而收益是修 12.5% 的用例。
2. **现产品里这个修复根本用不上**：`app/engine/scheduler.py:369` 只在 `total >= 2048` 时启用精确尾部
   （`EXACT_TAIL_MIN_PROMPT = 2048`），而失败的 prompt 是 64–128 token。要用它，必须先改这个阈值，
   而那会把 +0.79 s 加到**所有**短 prompt 上 —— 短 prompt 恰恰是首字最敏感、也是 2396 里收益最大的
   一档。**这一条是本阶段最需要让决策者看到的约束。**
3. 若确实要在低余数上补精确回放，最小可行形态是「**只补到 16 行，且只对 `n%64 < 16` 的 prompt 补**」，
   代价就是表 2 的 A/C 档（+0.77~0.79 s）。仍不便宜，但比全局启用便宜得多，且只影响本就会出错的那 1/8。
4. **根治仍是厂商修预填充图 MoE 算子**（第 0 层余弦 0.75 → 0.9999）。在那之前，这个问题没有便宜的解法。
5. **不要再把「对齐放宽到 16/32」当成净收益**：2396 已经测出它掉 5 条正确率，本阶段进一步说明
   「用精确尾部去补偿」的代价比收益还大。两条路要么都别走，要么先解决 MoE 精度。

## 与任务卡的偏差

1. **low 集新增了一个填充池 `SHORT_PAD`（15 句中性短句），且 `--set low` 会用它。**
   卡要求在 `mid` 之外生成第二套满足 `n%64 <= 7` 的用例；实测只靠 `mid` 原有的
   `A_QUESTION_PAD` / `GENERIC_PAD`（单句 11–24 token）只能命中少数余数，15 条 A 里只能凑出 1 条
   落在窗口内。加入按 token 长度错开的短句池后 40/40 全部命中。**`mid` 集的生成路径完全不受影响**
   （`pad_pool()` 在 `SET == "mid"` 时返回原池），40 个 id 文件与 `cases.json` 逐字节未变。
2. **`mid` 的 `cases.json` 保持 2396 的键集合，没有加 `set` / `rem_min` 等新字段。**
   卡的硬约束是「原有那套的输出必须逐字节不变」，加字段会破坏它。新字段只写进 low 的
   `cases.json`；两个窗口定义放在 `gen.SETS` 里，测试从那里读。这是我在「可读性」与「逐字节不变」
   之间选了后者，因为后者是卡的明确要求。
3. **low 集的 C 类追问是 64–70 token，历史 201–238 token**，都满足卡的约束
   （追问 64–71、历史 ≤ 2048）。历史比 `mid` 略短（221–272）是因为追问变长后同一次渲染里
   可用给历史的空间相应变化，属预期。
4. **R2 的 C 类 c03 出现「通过 → 失败」，我按卡的要求如实列出，没有为了好看的对比删掉它。**
   卡问的是「能否修复」，答案是「部分修复」，39/40 是这个答案的正确表达。
5. **复跑范围**：卡要求对 R1 失败的用例用 `--only` 单独重跑 R1 和 R2。R1 失败 5 条 + R2 唯一的失败
   1 条（c03）一起复跑，两个方向都覆盖了。
6. **未改 `native/`、`app/`、`web/`、默认配置、`/opt/sophgo/cv84x6_llm_server`；未访问 2282。**
   `--exact-tail` 是评测脚本的参数，引擎侧只调既有的 `llm_session_set_exact_tail`，
   没有 patch 任何 C/C++ 代码。
