# D7 修复：堆余量下限（MYS-2703）

> 第 2、3 步的原始数据与结论。第 1 步（那条命令的身份）见
> [`step1-stuck-command.md`](step1-stuck-command.md)。

## 一句话

**卡死的充分变量是「NPU 堆余量」这一个数，不是「哪个模型在场」、也不是前缀缓存。**
5 模型 + 一个只占不用的压舱物把余量压到 280 MiB，照样 136 s 卡死；
6 模型关掉前缀缓存，照样 125 s 卡死。把余量放到 640 MiB 以上，
同样的 `chat×2` 跑 12 分钟干净。

修复因此落在**准入**上：任何一次加载都必须给 NPU 留下至少 1 GiB。

## 第 2 步：拆开两个条件

### 2a 压舱物实验（模型种类 vs 堆余量）

R15 原本「5 模型 + chat×2 = 干净」，但 5 模型比 6 模型多出约 2 GiB 余量，
两个变量同时在动。压舱物只动第二个：

| 组 | 驻留 | 压舱物 | NPU 余量 | 结果 |
|---|---|---|---|---|
| B1 | 5 模型（无 VL） | 2153 MiB（只占不用） | **279 MiB** | **136 s 卡死，0 个请求完成** |
| — | 6 模型（R11 基线） | 无 | 280 MiB | 125–140 s 卡死（本次 T1/T2/T3 共 3 次） |

**结论：「堆满」本身就是条件，与第 6 个模型（VL）无关。** B1 里 VL 根本没加载，
堆余量一样，卡死时间一样，卡住的命令也一样（`lm_head`，pid 34556，
`block_cache_39 → sync rc=0 → lm_head` 之后无返回）。

压舱物是 `tools/e2e/ballast.c`：`bm_malloc_device_byte_heap_mask(handle, &m, 1, N)`
之后只 sleep，不读不写。它是独立进程，不进任何 worker 的堆。

### 2b 前缀缓存实验

R11 配置（6 模型 + `chat:2`），把前缀缓存关掉（`prefix_cache_max_mb=0`、
`prefix_cache_entries=1`，经 `POST /api/settings` 生效并在 `/api/settings` 回读确认）：

| 组 | 前缀缓存 | NPU 余量 | 结果 |
|---|---|---|---|
| C1 | **关**（0 MiB / 1 条） | 280 MiB | **125 s 卡死，0 个请求完成** |

**结论：前缀缓存不是条件。** 关闭它之后卡死照旧，时间与 R11 相同。
这同时否定了任务卡里「堆不够时 `ensure_park` 反复申请释放」这条猜测作为**触发条件**的可能
—— 卡死不需要 park/unpark 参与。

## 第 3 步：修复

### 3a 为什么修准入，而不是修命令序列

第 1 步证明卡住的是 `lm_head`（4 核图），且它前面 40 层和 `sync` 全部正常返回。
任务卡列的 b 方向（「在单核网络之前多做一次同步」）前提不成立：
`lm_head` 不是单核，也没有「4 核批次紧接着单核」这种结构——每个 decode 轮都是
40 层 + `sync` + `lm_head`，卡死时那一轮的 `sync` 已经 `rc=0` 回来了。

a 方向（给 d2d/memset 加返回值检查）**已经做了**，但它不是修复：本次所有卡死现场里
d2d 和 memset 全部 `rc=0`（T2：1216 次 d2d、3216 次 memset，无一失败），
它们只是「可能导致更晚才暴露」的隐患，不是这次的病因。检查留下，作为防御。

c 方向成立：**堆余量是条件，那么就在准入里守住它。**

### 3b 实现

`app/core/models.py`：

- 新常量 `NPU_RESERVE_DEFAULT_BYTES = 1024 MiB`，可用 `CV84X6_NPU_RESERVE_MB` 覆盖，
  `0` 关闭；
- 新方法 `ModelManager._check_npu_reserve(info)`，在 `_load_locked` 里
  `_check_npu_admission` 之后调用。

判据只有一行算术：

```
NPU 当前空闲 − 本次加载自身的占用 < R  →  拒绝（409 / device_memory_insufficient）
```

三个设计点，每个都有理由：

1. **减去本次加载的占用**。「当前空闲是否 ≥ R」问的是「装得下吗」，
   这正是原有 `_check_npu_admission` 已经回答的问题——而它对 6 个模型全部回答了「装得下」，
   板子照样两分钟就死。要问的是「装下之后还剩多少」。
   这个 bug 我第一版就犯了：在板上实测发现 6 个模型全被放行，才改成减法。
2. **对 chat 也生效**。原有准入对 chat 直接 `return`（chat 的 bmodel 占用无法从文件大小估）。
   这里用的不是估算而是 `static_bytes()`——35B 的 22752 MiB 从上一次加载实测得来，
   这是加载路径上本来就在用的数。故障恰恰发生在 chat 上，不能跳过它。
3. **只比 NPU 堆**。VPP 在全部 MYS-2693 现场都停在 256 MiB 启动保留上，从没装过模型；
   把 VPP 算进来会让「NPU 剩 280 MiB、VPP 剩 3838 MiB」被判成「还有 4 GiB」，正好放行卡死配置。

### 3c 阈值 R：实测扫描

方法：固定负载（5 模型 + `chat:2`），用压舱物把 NPU 余量调到目标值，
每组 12 分钟。**只变余量这一个数。**

| NPU 余量 | 时长 | 请求/成功 | 结果 |
|---|---|---|---|
| ~280 MiB | 136 s | 0 / 0 | **卡死** |
| **512 MiB** | 135.8 s | 0 / 0 | **卡死** |
| **640 MiB** | **12 min** | **398 / 398** | 干净 |
| **1024 MiB** | **12 min** | **404 / 404** | 干净 |
| 2432 MiB（未加压舱物） | 12 min | — | 干净 |

边界落在 512–640 MiB 之间，没有进一步二分（每点 12 分钟 + 一次重启，
而且卡死点本身不可逆）。默认值取 **1024 MiB**，比已知能活的 640 再高一档：
这个故障的既有证据是「20 分钟干净不等于几小时干净」（MYS-2693 R17 跑了 130 分钟
才在 3493 次请求上卡死），贴着悬崖设默认值没有余量。

### 3d 板上验证

在装好的 v0.6.29 上（只替换 `app/core/models.py` 与 `app/core/errors.py`，
安装包与版本号未动），按 R11 的 6 模型顺序加载：

```
qwen3.6-35b-a3b-128k   200
qwen3-embedding-0.6b   200
bge-reranker-v2-m3     200
qwen3-asr-0.6b         200
ppocrv6-medium         200
paddleocr-vl-1.5       409  ← 拒绝
{"detail":"NPU 显存余量不足：加载 paddleocr-vl-1.5（约 2385 MiB）后
 NPU 只剩 -105 MiB，低于安全下限 1024 MiB。…当前已加载：bge-reranker-v2-m3,
 ppocrv6-medium, qwen3-embedding-0.6b, qwen3.6-35b-a3b-128k。…",
 "code":"device_memory_insufficient"}
```

也就是说：**触发这次卡死的那个 6 模型配置，现在从 API 层面就装不出来**，
而且拒绝消息给出了模型、余量、下限和该卸载谁。

### 3e 性能代价

这个修复不改任何推理路径：它只在**加载**时多算一次减法，decode 的图、发射顺序、
同步点全部不变。所以它的代价不在「每个模型跑多快」，而在「能同时驻留几个模型」——
R11 那个 6 模型配置现在装不出来。

单会话 vs 双会话的 decode 吞吐（`chat`，96 token 生成，每档 3 轮，
板上直测 `/v1/chat/completions` 的 completion_tokens / 墙钟）：

| 并发会话 | 聚合 tok/s | 每会话 tok/s |
|---|---|---|
| 1 | **24.98** | 24.83 / 25.06 / 25.05 |
| 2 | **24.44** | 12.75 / 12.66 / 12.68（另一路 12.22 / 12.21 / 12.22） |

**这是本次一个顺带的、但不该被忽略的发现：同 worker 双会话几乎没有聚合收益**
（24.98 → 24.44，降 2%），而每个会话的速率**减半**。原因在引擎结构里：
`Session::decode()` 整枚 token 期间持有 `Engine::mu`，两个会话只能轮流跑，
每轮还要多付一次 park/unpark 的 d2d。也就是说 `max_concurrent_per_model=2`
买到的是「两个会话都不会被饿死」，不是「吞吐翻倍」。

这条对取舍有直接影响：把 35B 的并发降到 1，几乎不损失总吞吐，
却能把堆需求降下来——它也是本任务兜底方案（3d）成本很低的原因。

## 3f 60 分钟验证（入选方案的验收）

修复装到板上之后，用**修复允许的最大配置**跑 60 分钟
（`/data/mys2693/runs/S60`，`chat:2`，与 R11 同样的负载形状）：

| 项 | 实测 |
|---|---|
| 时长 | **3600.5 s（60 min）** |
| 请求 / 成功 | **2027 / 2027，全部 200** |
| 卡死 | **无**（`hang.detected=false`） |
| `dmesg` `wait api timeout` | 前后都是 **0** |
| `dmesg` Oops | **0** |
| NPU 堆 | 起始 28516 MiB 已用，结束 26724 MiB |
| 结束探针 | chat/embed/rerank/ocr 全 200 |

对照：同一块板、同样 `chat×2`、6 模型的 R11 **125 s 就卡死、0 个请求完成**；
本次修复把「余量不足」这个前置条件从准入上拿掉之后，2027 次请求一次没卡。

**注意这不是「消除了驱动缺陷」**：驱动/固件那条 `bmdrv_thread_sync_api` 的问题
（MYS-2693 报告）依然在。修复做的是不让应用层把设备推到那个状态。
如果绕过准入（`CV84X6_NPU_RESERVE_MB=0`）把堆重新占满，卡死会照旧发生。
