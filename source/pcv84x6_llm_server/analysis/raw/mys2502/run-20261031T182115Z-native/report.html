直白回答（本模式）

在 18 次窗口内请求上，v0.6.13 全部以 409 拒绝，没有一次进入半初始化的 worker；窗口后的 6 次对照请求中 6 次返回正常摘要。也就是说：在这个模型、这组时机上，未加载完毕时推理不会得到异常输出，而是直接被拒绝。现场「两个女生约好一起出门……」那类异常输出，本轮没有在本设备复现，不能据此宣称已复现根因。

原生 + 插桩：两半合起来的结论

这个问题在原生发布包上测不到：窗口只有几毫秒，比一次 admin 轮询还窄。 所以结论必须由两个实验共同给出，缺一半都不能下判断。

实验窗口内尝试409 拒绝 被放行被放行后的输出
原生（发布包原样） 1818 0 全部正常摘要
插桩（窗口人为放大） 63 3 全部正常摘要

结论一（缺陷真实存在）：插桩实验里窗口被放大后，三个接口 3 次请求全部被放行并进入了 worker （发送瞬间模型自报 loaded=true, operation=loading）。 这证明「模型已发布 loaded、但能力探测尚未结束」这个状态确实可以被未加准入门控的旧版放行—— 不是推测，是实测。

结论二（原生条件下几乎打不中）：原生实验里窗口内 18 次请求全部得到 409，放行 0 次。 原因不是门控存在（v0.6.13 并没有 v0.6.14 的 require_ready）， 而是这个窗口本身只有 7.04 ms（8 个时机实测 6、5.2、5.3、10.1、6.7、5.2、11.7、6.1）： loaded=true 发布后紧接着就是能力探测的两次本机 RPC， 期间 operation 仍为 loading，而 _resolve_model 只检查 loaded——所以「能不能进」取决于请求是否恰好落在这几毫秒里。

原生 `edge` 时机的实测边界：本次运行确实观测到了 loaded=true, operation=loading 这个状态，窗口宽 23.0 ms。但三个接口的请求发出时，窗口已经关闭 +3.4、+8.6、+12.4 ms（负值表示早于关闭时刻；这里是正值，即已关闭之后）。因此它们全部落在窗口之后、得到 200 正常摘要，放行计数仍为 0——这是边界未命中，不是「窗口拦住了」。窗口内实际被放行的次数见上表的插桩实验。

结论三（放行后的输出没有异常）：被放行的 3 次请求，输出与 ready 对照组逐字相同（同一 prompt、同一 token 数）。 原因在 worker 侧：它先把权重载入 NPU、再 sched.start()、最后才 start_server() 打开 socket，并且 sched.start() 是 create_task 不阻塞。所以服务端「loaded」与「socket 已开」是同一时刻， 能进 worker 的请求，其引擎与调度器都已在跑。这就是「被放行但输出正常」的机制解释。

因此，现场那一次异常输出不能用这条竞态解释。本轮没有复现 「两个女生约好一起出门……」同款异常，也没有任何证据把它归因到加载竞态。 样本量与其它可能原因见「局限」。

局限与不声称的事

  • 模式：原生模式：直接打 v0.6.13 发布包，服务端没有任何改动或人造延迟。窗口宽度完全由服务自身决定；因此 edge 时机能否命中取决于一次 admin 轮询能否落进那个窗口，未命中的行在表中如实标注为「窗口内=否」。
  • 样本量：每个时机每个接口只发一次请求。这不是统计意义上的采样， 而是「该时机下这一次发生了什么」的事实记录。多次重复会占用数十小时的设备时间。
  • 时机与阶段的关系：目标延迟只是「请求发出的时刻」，不是「模型处于哪个初始化阶段」。 真实阶段由表中「发送时模型状态」与「就绪差」说明，报告不把延迟名称当成阶段名称。
  • 轮询分辨率：`edge` 时机依赖对 `/api/models` 的轮询，分辨率受 admin GET 往返时间限制。 观测到的窗口宽度写在「每次加载的时序采样」表里；如果窗口比一次轮询还窄， 报告会明说「从未观测到」，而不是假装命中。
  • 复现边界：现场异常发生在另一台设备的 v0.6.12 上，且当时没有留下任何请求/回复内容。 本报告测的是同一代码路径在 v0.6.13 上的行为，不等于复现了那一台设备的那一次。
  • 解码缺陷：U+FFFD 是已知的独立缺陷（MYS-2510/MYS-2520），已单列， 不参与加载竞态的判定。
