v0.6.13/v0.6.14 都存在流式逐 token 解码缺陷：被拆到两个 token 的字符会输出 \ufffd（证据见 MYS-2510：门簪 → 门\ufffd\ufffd）。 本表把它与「加载竞态导致的异常」分开：只有当对照组的输出干净、而窗口内出现异常时， 才可把异常归因于竞态。本轮如果两组都出现 \ufffd，那是既有缺陷，与加载无关。 修复在 MYS-2520 并行进行，本任务不改产品代码。

局限与不声称的事

  • 模式：插桩（测试构建）模式：同一发布包，以 sitecustomize.py 延迟 WorkerClient.health 8.0 秒启动。该调用在 v0.6.13 中只有一个调用方——_load_locked 的能力探测，位于 loaded 发布之后、operation 清空之前。因此放大的是状态机自己的「已发布未就绪」窗口，其它任何路径（/api/models、/api/stats、readiness 握手）都不经过它。其结论只描述窗口被放大后的旧版行为，不能当作原生时序证据；原生行为请看 native 报告。
  • 样本量：每个时机每个接口只发一次请求。这不是统计意义上的采样， 而是「该时机下这一次发生了什么」的事实记录。多次重复会占用数十小时的设备时间。
  • 时机与阶段的关系：目标延迟只是「请求发出的时刻」，不是「模型处于哪个初始化阶段」。 真实阶段由表中「发送时模型状态」与「就绪差」说明，报告不把延迟名称当成阶段名称。
  • 轮询分辨率：`edge` 时机依赖对 `/api/models` 的轮询，分辨率受 admin GET 往返时间限制。 观测到的窗口宽度写在「每次加载的时序采样」表里；如果窗口比一次轮询还窄， 报告会明说「从未观测到」，而不是假装命中。
  • 复现边界：现场异常发生在另一台设备的 v0.6.12 上，且当时没有留下任何请求/回复内容。 本报告测的是同一代码路径在 v0.6.13 上的行为，不等于复现了那一台设备的那一次。
  • 解码缺陷：U+FFFD 是已知的独立缺陷（MYS-2510/MYS-2520），已单列， 不参与加载竞态的判定。
