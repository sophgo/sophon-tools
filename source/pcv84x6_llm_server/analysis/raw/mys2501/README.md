# MYS-2501：128k 模型扩大稳定性测试（`.151` 真机）

MYS-2496 阶段 4。目标是回答两个问题：**这个版本在 128k 模型上连续跑 2100 次还稳不稳**，
以及**模型没加载完时推理请求到底进不进得去**。

- 设备：`linaro@172.26.166.96 -p 10151`，SN `HQDZCVEBFJIJA0027`
- 版本：`0.6.14`（deb `0.6.14`，`/healthz` 自报 `0.6.14`）
- 模型：`qwen3.6-35b-a3b-128k`，`context_length=131072`，`supports_sampling=false`
- 内存布局：TPU 26,644 MiB / VPP 500 MiB，MemTotal 3,995,000 kB（本轮未再改动内存）
- 工具：`tools/extended_stability_suite.py`

## 结论

**判定通过（PASS）。** 2100 次请求全部正常结束，无 5xx、无连接异常、无空回复、无串话，
每条请求恰好一条匹配的推理记录；readiness 窗口内 657 次推理尝试**全部** 409，没有一条
进入 worker，也没有写出一条记录。

| 项 | 结果 |
|---|---|
| 核心 2000 次（无上下文 1000 + 带上下文 1000） | **2000 / 2000** 正常结束 |
| 带上下文构成 | **100 个独立会话 × 每会话 10 轮**（不是 1000 轮同一会话） |
| 并发 2 路 × 50 轮 | **100 / 100** 成功，串话 0，标记回显 99/100（1 次回答仅数字未含标记） |
| HTTP 5xx / 连接异常 / 空回复 | 0 / 0 / 0 |
| 推理记录一致性 | 逐条核对 2100 条：缺失 0、重复 0、输入不一致 0、输出不一致 0、token 不一致 0、key 泄漏 0；只读 SQLite 命中 2100/2100 |
| readiness 窗口 | 657 次尝试 **657 次 409**，放行 0；worker generate 0；新增记录 0 |
| 加载完成后短请求 | HTTP 200，恰好新增 1 条记录 |
| 重新加载耗时 | 66.35 s |

### 正确性（单独列出，不参与稳定性判定）

| 指标 | 结果 |
|---|---|
| 计数正确 | **1832 / 2000 = 91.6%** |
| 上下文回忆正确 | **397 / 400 = 99.25%** |

回忆率接近满分是**历史真的被用了**的证据：300 字档起每轮追问上一轮植入的关键词，
这只有在整段历史被重发并被模型实际读到的情况下才答得对。

91.6% 的计数正确率**不是**稳定性判据，任务卡也没有设正确率门槛。错的那 168 次集中
在长档（400 字档 32/83、300 字档 67/83、200 字档 69/83）：材料更长、目标词出现次数
需要真正数，模型会多数或漏数。这是**任务难度**，不是服务故障——同一批请求的
HTTP、记录、token 全部一致。**缓存命中数（cached）不作为语义正确的证据**：
前缀复用只说明 KV 被复用，不说明答案对。

## readiness 专项：模型没加载完时请求会怎样

做法：用管理 API **正常停止**（SIGTERM，未使用任何强杀）→ 触发重新加载 → 在加载
窗口内**持续**对三个推理接口发请求，直到 `/api/models` 报告就绪。

三个接口：`/v1/chat/completions`（stream 与非 stream）、`/api/chat/stream`（控制台）。

| 接口 | 尝试 | 409 拒绝 | 加载期间被放行 | 其他状态 | 携带 req_id |
|---|---|---|---|---|---|
| stream | 219 | **219** | 0 | 0 | 0 |
| nonstream | 219 | **219** | 0 | 0 | 0 |
| console | 219 | **219** | 0 | 0 | 0 |

- 观察到 `operation=loading`：**是**（不是伪造的加载状态，是真实加载窗口）。
- 新 worker 就绪时它自己的 generate 计数：**0**——比 HTTP 状态更硬的证据，
  说明**没有任何请求真的进到模型**。
- 加载窗口内推理记录新增：**0**。
- 加载完成后短请求：HTTP 200，`req_id` 存在，新增记录**恰好 1 条**，输出「2」且计数正确。

结论：**0.6.14 的准入闸门在真机上成立**。加载中的请求在网络层就被 409 拒绝，
不会进入半初始化 worker，也不会污染推理记录。

### 这一轮之前，闸门测试本身有 4 个 bug

readiness 是本次新增的能力，第一版工具在真机上**连错三次**，每次都是工具的问题而不是
服务的问题；这三个失败运行保留在设备上，不覆盖：

| 现象 | 真因 | 修法 |
|---|---|---|
| 加载窗口跑完后整个阶段崩掉 | 探测请求用 900+ 轮次编号，30 字档放不下四位数轮号+材料，prompt 生成器正确拒绝 | 探测改用一个固定 prompt；生成器在档位太紧时换更短的目标词重算余量 |
| `readiness_admitted=1` | 探测每轮只查一次就绪、再连发三个请求；66 s 加载在第三次请求前完成，那个 200 发生在服务 `loaded_at` **之后 1.5 ms** | 按**时间戳**判定是否在窗口内；每个接口前重新查一次就绪 |
| console 接口永远 401 | 探测用了未登录的客户端，`/api/chat/stream` 是 cookie 鉴权 | 探测客户端先登录 |
| 窗口内 generate 计数是负数 | 重载会换进程，"新 worker 值 − 旧 worker 值" 无意义 | 读新 worker 就绪时的**绝对值**（0 即没进过推理） |

另外两次是**沿用证据**时的 bug：JSONL 不存 prompt 原文（manifest 存），沿用后记录
核对拿空串比对，报了 2100 条假的"输入不一致"；修法是按 SHA-256 从 manifest 回填并校验。

## 与任务卡的偏差

1. **并发只到 2 路**：任务卡明确要求 2 路 × 50 轮、且要求不要并发 3。已遵守。
   这意味着 3 路的行为本轮**没有覆盖**。
2. **1000/1200 两个长度档只有无上下文组覆盖**。带上下文组每会话 10 轮走 2–800，
   因为让一个会话涨到 1200 字档会让后期每轮都变成十万 token 级预填充，
   测到的是预填充上限而不是稳定性。这是设计取舍，已在报告中写明。
3. **核心 2000 次来自一次完整运行，readiness 来自另一次运行**（`025800Z` 沿用
   `002142Z` 的 2100 行请求证据）。原因是 readiness 阶段的工具 bug 在核心组跑完
   之后才暴露；重跑核心组既浪费两个半小时，也会用第二次采样覆盖第一次的真实证据，
   而任务卡明确禁止后者。合并后的报告在「证据构成」里如实写明来源，两段请求各自
   保留真实时间戳。
